Multi-Agent Systems: When One AI Agent Isn't Enough, and How Not to Over-Engineer

AI AgentsAugust 13, 2026 · 8 min read

The term "multi-agent system" sounds impressive, and contractors are happy to use it: several AI agents, each with its own role, talk to one another and solve the task together. In a presentation it looks convincing. In practice, most small business tasks are solved by one agent with good tools, and a multi-agent architecture adds cost, latency and new points of failure. But there are situations where you really can't do without one.

This article is about how to tell one from the other: when one agent isn't enough, what a sensible multi-agent setup looks like, and the signs that a project is over-engineered.

What a multi-agent system is, in plain terms

A single agent is a language model plus a set of tools: access to the CRM, email, a database, a calculator. It receives a task, plans the steps, calls the tools and returns a result.

A multi-agent system is several such agents, each with its own role, its own instructions and its own set of tools. One sorts incoming emails, another checks stock levels in the warehouse, a third writes the reply to the customer, a fourth checks that the reply doesn't break the rules. Their work is coordinated either by a dispatcher agent or by a predefined task handoff scheme. The frameworks for this are LangGraph, CrewAI and the like.

The team analogy fits, but with a caveat: agents are no smarter than their instructions, and every handoff between them is an extra model call that costs money and time and can introduce an error.

When one agent really isn't enough

Signs that the task has outgrown a single-agent setup.

The instructions have become contradictory

If one agent has to sell, and check compliance with legal restrictions, and write briefly, and explain in detail, the instructions swell to a dozen pages and the model starts getting confused. Splitting it into "one writes, another checks" removes the conflict of roles.

Too many tools

When an agent has thirty different actions available, it picks the wrong one more often. A rule of thumb from practice: more than 10–15 tools for one agent is a reason to think about splitting by domain, for example "everything about the warehouse" and "everything about customers."

An independent check is needed

In tasks involving money, contracts and medical data you need a controller that took no part in preparing the answer. A reviewer agent with separate instructions — "find errors and violations" — catches what the author misses.

Parts of the task can be done in parallel

If you need to query three different sources at the same time — supplier websites, a database and email — parallel agents save waiting time.

Different requirements for the model

Email classification can be done by a cheap, fast model, and drafting a complex reply by an expensive one. Different agents mean different models, which cuts the API bill severalfold.

Typical patterns that actually work

Three architectures take root well in small and medium businesses.

Dispatcher and specialists. An incoming request goes to a router agent, which determines the type of task and passes it to one of the specialists: sales, support, accounting questions. An example is a single company Telegram channel that both customers and employees write to. This is the most common and the most understandable pattern.

Pipeline. The task passes through several agents in sequence. An example from document workflow: one agent recognizes an incoming invoice, a second matches it against the contract and the order, a third generates the accounting entry and a notification to the accountant. Each step is verifiable, and a failure is easy to localize.

Author and critic. One agent prepares the output — a quote, a reply to a customer, a draft contract. The second checks it against a list of requirements and either sends it back for revision or lets it through. Two or three rounds at most, otherwise you get an endless argument.

"A society of agents that talk freely among themselves and decide for themselves who does what" looks impressive in demos but is hardly used in business: the result is unpredictable, and the cost of a single task can grow tens of times over.

Example: what this looks like in a real project

Take a real estate agency that collects listings from many Telegram channels and shows customers curated selections. The task is similar to what we at AiKrok did in the Batumi Rent project. Let's break the process down into roles.

  • The collector reads the channels and picks out messages that look like listings. A simple task — a cheap model, or rules with no AI at all.
  • The structurer turns the text of a post into a card: district, price, rooms, floor, contact. This needs a stronger model.
  • The deduplicator compares a new card with existing ones and decides whether it's a repeat. Part of the work is vectors and rules, part is a model for borderline cases.
  • The notifier matches cards against customer requests and sends a push.

Note: of the four roles, only two require a language model, and none requires the agents to "discuss" anything among themselves. It's a pipeline with clear interfaces. This is exactly what sensible multi-agent design looks like. More on the task in our article on automation for a real estate agency.

How not to over-engineer: signs and rules

Signs that a project is sliding into excessive complexity:

  • there are more than five agents in the scheme, and the task is to answer a customer's question about delivery;
  • the agents pass the task to each other in a circle, and nobody knows how many rounds there will be;
  • the cost of one handled inquiry has grown severalfold compared with the single-agent version;
  • when an error occurs, it's impossible to tell which agent made it;
  • the contractor spends longer explaining the architecture than the business problem.

Rules that help keep the system within bounds:

  1. Start with one agent. Split only when you've hit a specific limitation, not in advance "to grow into."
  2. Fix the handoff scheme. Who passes what to whom is written down in advance, not decided by the model on the fly.
  3. Limit the loops. Any "author — critic" loop has a maximum number of iterations.
  4. Take deterministic logic out of the agents. If something can be decided by a rule or a database query, a model has no place there.
  5. Log every step. Every task should leave a clear trail: what each agent saw and what it decided.

Cost and speed: what you're rarely warned about

Each agent is at least one model call, and more often several. If single-agent handling of an inquiry cost, say, one unit, a pipeline of four agents will cost roughly three to six units, and a free-discussion scheme — an unpredictable amount. Latency adds up too: four sequential steps of five seconds each is twenty seconds of waiting for a customer in a chat. For background processes this doesn't matter; for a live conversation it's critical.

That's why in customer-facing channels the aim is to keep one agent on the line and the rest in the background. For the structure of agent costs in general, see our article on how much an AI agent costs.

Summary

A multi-agent system is not a sign of a project's maturity and not an argument in a contractor's favor. It's a tool for specific situations: a conflict of roles in the instructions, too many tools, a need for an independent check, parallel processing or savings from using different models. If none of these situations has arisen for you, one agent will do the job better, more cheaply and more predictably. And if one has, choose a simple pattern: dispatcher, pipeline or author with critic, with a strictly defined task handoff and logs at every step.
